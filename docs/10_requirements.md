# 10. 要件定義

## 用語

| 語 | 意味 |
|---|---|
| **work** | 作品（アニメ・劇場アニメ・ゲーム） |
| **location** | 実在の場所（駅、神社、坂、店舗、橋 など） |
| **appearance** | 「この作品のこの場面に、この場所が出た」という対応関係。work × location の中間実体 |
| **confidence** | その appearance がどれだけ確かか（confirmed / likely / disputed） |
| **visitability** | その location に実際に入れるか（public / limited / private / closed） |

**work と location は多対多。** 1つの踏切に複数作品が出るし、1作品に数十の場所がある。
appearance を独立した実体として持つのが設計の核心で、ここを手抜きすると後で作り直しになる。

## 機能要件

### F1. 検索・絞り込み（本体）

以下の軸で **AND 絞り込み**ができること。軸の数がこのプロダクトの価値そのもの。

| 軸 | 型 | 備考 |
|---|---|---|
| 作品 | 複数選択 | 英題・原題・ローマ字・略称のすべてで引ける（"Your Name" / 君の名は。/ Kimi no Na wa） |
| 都道府県 / 市区町村 | 複数選択 | |
| **起点からの所要時間** | スライダー（〜30分/〜60分/〜90分/〜3時間/それ以上） | 起点は東京駅・新宿駅・大阪駅・京都駅から選択 |
| **訪問可否** | public / limited / private / closed | **デフォルトで private と closed を除外する** |
| カテゴリ | 駅・神社仏閣・学校・商店街・店舗・橋/踏切・公園・自然・その他 | |
| 車が必要か | boolean | 公共交通で行けるかは海外旅行者の最大の関心事 |
| 入場料 | free / paid / 不明 | |
| **最終検証日** | 6ヶ月以内 / 1年以内 / すべて | 鮮度を売りにするので前面に出す |

**要件**：フィルタ操作はサーバー往復なしで即時反映（クライアントサイド処理）。
URLに状態を反映し、絞り込み結果のURLがそのまま共有・被リンクの対象になること（SEO上も重要）。

### F2. 地図表示

- 絞り込み結果を地図にプロット。ピンのクラスタリング必須
- ピンをクリック → 場所名（英/日）、出た作品、徒歩分数、訪問可否、最終検証日、出典リンク
- **住所の日本語表記を必ずコピー可能な形で出す**（タクシー運転手・現地の人に見せるため）。
  これは実際の旅行者の行動に直結する、地味だが効く要件

### F3. ルート生成とエクスポート（差別化の核）

- 絞り込み結果 or 手動選択した location 群から、**1日で回れる順路**を生成
- 出力形式：
  - **Google マイマップ用 CSV / KML**（最も使われる）
  - **GPX**（登山・自転車勢）
  - **印刷/オフライン用 PDF**（日本語住所・最寄り駅・所要時間つき）
- 順路の計算は厳密でなくてよい。**最寄り駅でグルーピングし、路線順に並べる**程度で実用に足る
  （経路APIは課金が発生するので Phase 2 まで使わない。`30_architecture.md` 参照）

### F4. 作品ページ / 場所ページ（SEOの受け皿）

- `/anime/{slug}` — その作品の全ロケーション（地図＋一覧＋「東京から日帰り可能なもの」抜粋）
- `/location/{slug}` — その場所に出た全作品、アクセス、マナー注意、出典
- `/prefecture/{slug}` — 都道府県別
- 静的生成し、それぞれ独立してインデックスされること。**ここが検索流入の主戦場**

### F5. 更新アラート（Phase 2、課金の芽）

- 「この作品に新しいロケーションが追加されたら通知」
- 「この場所の状況が変わったら通知（閉業・立入禁止化）」
- メール配信。ここが唯一の継続課金の根拠になりうる

### F6. 多言語（Phase 2）

需要の主力はアジア圏。**Phase 0 の時点でロケール分離だけしておく**（後付けは高くつく）。

- Phase 0-1: `en` のみ
- Phase 2: `zh-Hant`（香港・台湾）→ `ko` → `zh-Hans` の順。この順序は需要データに基づく
- 場所名・住所は元から日英を持っているので、翻訳対象はUI文言と注意書きのみ。安く済む設計にする

## 非機能要件

| 項目 | 要件 | 理由 |
|---|---|---|
| **ランニングコスト** | 月額 **$0**（ドメイン代を除く） | 検証が終わるまで固定費を作らない。有料APIは使わない |
| 表示速度 | LCP 2.5秒以内（3G相当・モバイル） | 主対象は移動中のスマホ利用 |
| モバイル | モバイルファースト。地図とフィルタが片手で操作できること | 現地で開かれる |
| **オフライン耐性** | 一度開いたページはオフラインで再閲覧できる（Service Worker） | 海外SIMや地下鉄で使われる |
| データ更新 | 週1回の自動収集＋差分レポート。**自動で本番反映はしない**（人間のレビューを挟む） | 誤データは信頼を一撃で壊す |
| 可用性 | 静的配信のみ。DBサーバー・APIサーバーを持たない | 障害対応の責任を負わない |
| 計測 | Cloudflare Web Analytics（Cookieなし） | GDPR同意バナーを出さずに済む＝UXと責任の両方で有利 |
| アクセシビリティ | 地図が使えない環境でも一覧表だけで用が足りること | |

## データ品質要件（このプロダクトの生命線）

1. **座標は必須。** 座標のない location はデータベースに入れない
2. **出典URLは必須。** 出典1件以上ないappearanceは `disputed` 扱いで非公開
3. **最終検証日を全レコードに持つ。** 表示もする
4. **確度を隠さない。** `likely` は likely と表示する。断言しないことが、
   長期的には断言する競合より信用される
5. **削除ログを残す。** 閉業・立入禁止化した場所は消さず `closed` にして理由と日付を残す。
   「行けなくなった」という情報自体に価値がある
