# 60. ロードマップと撤退基準

**縦割りで進める。** 「全部のデータを集めてから、サイトを作る」をやらない。
1作品ぶんのデータ → 表示 → 絞り込み → エクスポート、を先に**縦に1本通す**。

---

## Phase 0：検証（**2週間・実費ドメイン代のみ**）

目的は「作ること」ではなく「**行動で支払い意思の前段を測ること**」。

### タスク

| # | タスク | 完了の判定 |
|---|---|---|
| 0-1 | **データ源の実在確認**：東京・神奈川・埼玉・千葉で、構造化可能な一次情報が何件あるか実際に数える | 数えた結果を `docs/71_source_survey.md` に記録。**150件に届かないならこの企画は中止** |
| 0-2 | **競合の実測**：英語圏の上位10サイトを実際に触り、「作品名で引いて座標が出るか」を採点 | 採点表を `docs/72_competitor_audit.md` に記録。**触らずに評価しない** |
| 0-3 | 作品10本を選定（選定基準＝海外配信の有無 × ロケーション数。国内人気順で選ばない） | `config/works.yaml` |
| 0-4 | 縦に1本通す：1作品ぶんのデータを手作業でYAML化 → Astroで作品ページを生成 → 地図に出す | `/anime/{slug}/` が本番URLで見える |
| 0-5 | 残り9作品ぶんを収集（半自動でよい。この段階では手作業を厭わない） | 150〜300 location |
| 0-6 | フィルタ（作品・所要時間・訪問可否）とトップの地図を実装 | 3軸で絞り込める |
| 0-7 | **「Export route」ボタンを設置**（機能は未実装でよい。押されたらメール登録に誘導） | クリックが計測できる |
| 0-8 | コミュニティに投下（Reddit r/JapanTravel・作品別sub、Discord、Threads）×3本 | 投稿済み |

### ゲート判定

| 指標 | 目標 |
|---|---|
| 累計クリック | 300 |
| Export route クリック率 | 5% |
| メール登録 | 30件 |

**3つのうち2つ以上を満たせば Phase 1 へ。満たさなければ撤退し、候補2（日本の制度・手続き差分トラッカー）に切り替える。**
「反応が薄かったのはコミュニティ選びが悪かったからだ」という延命をしない。
どうしても再試行するなら**1回だけ**、投稿先を変えて追試する。

## Phase 1：SEOの土台（1〜3ヶ月）

- 収録範囲を関西（京都・大阪・滋賀・兵庫）と、地方の代表格（秩父・沼津・大洗・飛騨）に拡大
- `/anime/{slug}/day-trip/` 系の派生ページを、**件数が閾値を超えた作品だけ**生成
- 場所ページ・都道府県ページの静的生成
- 収集パイプラインを自動化し、GitHub Actions で週1実行 ＋ **差分レポートを人間がレビュー**
- アフィリエイト導線をルート出力の中に埋め込む（`50_monetization.md`）
- `niche-keyword-finder` で英語ロングテールを検定してからページを作る（作ってから調べない）

**Phase 1 の判定**：3ヶ月で自然検索からの流入が発生しているか。ゼロなら構造を疑う。

## Phase 2：エクスポートと多言語（4〜9ヶ月）

- GPX / KML / Googleマイマップ用CSV / オフラインPDF を実装 → **買い切り $9 で販売**
- 更新アラート（メール）
- `zh-Hant` を追加（需要データ上、次に大きい市場）
- 収録 2,000 location

## Phase 3：拡張（10ヶ月〜）

- `ko` / `zh-Hans`
- 月間5万セッションを超えたらディスプレイ広告を検討
- ゲーム・実写ドラマ・映画のロケ地への拡張を検討（**データモデルは最初から対応できる形にしてある**）

## リスクと対処

| リスク | 兆候 | 対処 |
|---|---|---|
| **権利者からの削除要請** | 通知が来る | 争わず即削除。`40_legal.md` を守っていれば起きにくい |
| **公式（アニメツーリズム協会・自治体）が英語版を出す** | 公式サイトの英語化 | 正面から競合しない。**公式が持たない「アクセス時間」「訪問可否」「最終検証日」に寄せる**。むしろ公式データを出典として引く側に回る |
| 迷惑行為の助長を批判される | SNSでの言及 | `40_legal.md` の配慮ルールが機能しているか点検。批判は真に受けて設計に反映する |
| データが陳腐化する | 出典URLの404増加、閉業報告 | `verify.py` の死活監視。**最終検証日を表示する設計自体が防御になっている** |
| 訪日需要そのものが減退 | 訪日客数の継続的な減少 | 総量ではなく構成に賭けているので即死はしない。ただし2四半期連続で聖地関連の検索が落ちたら再評価 |
| 作業が長期化して飽きる | Phase 0 が2週間を超える | **超えた時点で範囲を削る。** 期限を延ばさない |

## 引き継ぎ時の注意（実装者へ）

- **`docs/40_legal.md` を先に読むこと。** 画像を1枚入れた時点で企画が終わる種類のリスクがある
- **Phase 0 の 0-1 と 0-2 を飛ばさないこと。** ここを飛ばして作り始めるのが最も高くつく。
  データ源が薄い／競合が既に十分ならば、作らないのが正解
- 期限と範囲は削ってよいが、**ゲート判定の基準を下げてはいけない**
